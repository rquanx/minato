# 模型目录、路由与推理

## 来源与目录

每个 `source` 对应一组 API 端点、凭证和使用范围。首版实现 CPA 的 `/v1/models`，以及 OpenCode Zen 与 Go 的独立目录适配器。每个适配器返回模型原始 ID、上游端点类型及可获取的能力信息。对同名模型保留来源边界，对大小写和空格原样比对。可人工登记已验证的模型，目录同步继续独立记录该模型是否出现。

后台默认每 10 分钟同步一次，加随机间隔并限制每个来源只能有一个同步任务。HTTP 超时 10 秒，按来源配置最大分页数。完整、解析成功的快照才更新目录。失败、未取完分页或从非空突变为空时保留之前的目录，空目录需要第二次独立成功确认。模型在两次间隔同步的成功快照中持续缺失后标为 `removed`，重新出现时恢复 `listed`。来源读取失败标记 `stale`，已发布路由可继续运行。明确停用来源由管理员操作，并触发相关路由重算。

目录状态与调用健康分别展示。`listed` 表示目录可见，运行时成功、熔断和错误作为健康信号。首版复用 LiteLLM 实例的冷却逻辑，并在 Minato 汇总实际调用结果。默认不定时发送计费探测，管理员可从测试页显式验证候选。

首版能力字段包括客户端端点、上游端点、文本上下文、流式、工具调用和结构化输出模式。上下文预算包含输入及预留输出。配置要求下存在未知能力时排除该候选，并在预览展示原因。结构化输出区分 JSON 对象和指定 schema。Responses 到 Chat 的转换只覆盖契约测试通过的参数子集。

## 生成并发布路由

1. 结合功能点声明、管理员覆盖和环境默认池，按「首选 → 功能点备用 → 默认池」排序，再按来源和模型去重。来源授权、模型下架、协议或能力不匹配的候选会被排除。默认最多保留三个候选，该上限可配置。每条候选保存来源、上游模型原始 ID、接口及凭证版本引用。
2. 目录变化或业务声明变化时，根据最近一次批准的策略自动重算。新模型满足已批准默认池条件时可加入候选。管理员调整首选和备用列表先保存草稿，再显式发布。预览给出候选和排除原因，并标明所用配置及目录版本。候选完全相同时跳过发布。
3. 发布任务为 `(feature_id, version)` 通过 LiteLLM `/model/new` 创建独立候选组。逐项读回校验，并保存有序候选与运行时引用。切换以数据库事务提交 `active_version` 为准，比较任务提交时的期望版本并拒绝过期任务覆盖较新配置。在途请求继续持有旧版候选列表。
4. 发布任务按功能点加锁。任务重试使用同一个版本和内部组 ID。状态为 `queued → preparing → verifying → active`，也可终止于 `failed` 或 `superseded`。失败的临时组由后台回收。旧组在超过最大请求期限并确认在途请求排空后回收，历史快照留存以支持重建。
5. 回滚用历史配置创建新版本，重新校验当前权限、模型和引用的凭证。目录确认旧模型下架时用该策略剩余候选生成可运行路由。若变更后没有任何可用候选，已有版本进入清晰标记的不可用状态，入口对新请求返回 `503`，旧版本继续保留供排查和恢复。单次同步失败沿用上一份生效路由。

本地验证确认 LiteLLM `v1.85.0` 能动态添加独立模型组。Proxy 内置回退也会对普通上游 `400` 生效。Minato 首版在自己的入口执行错误类型判断和尝试排序，LiteLLM 继续处理单次上游调用与格式转换。 [本地验证结果](../../tools/litellm-compat/README.md) · [LiteLLM 模型管理](https://docs.litellm.ai/docs/proxy/model_management)

## 请求生命周期

1. 分配全局请求 ID，校验环境 Key、别名和端点。根据同一份生效版本读取合同与 `runtime_ref`。首版直接读取 Postgres 已发布状态，保持撤销和切换对新请求即时生效。
2. 校验请求体大小、流式能力、支持的参数及环境限额。每次尝试将 `model` 改写为候选的内部模型组，以内部服务凭证和 `disable_fallbacks: true` 访问 LiteLLM。入口为每次尝试生成 `X-LiteLLM-Call-Id`，保存与 Minato 请求 ID 的关联。客户端提交的内部路由配置、上游地址、超时覆盖和权限相关元数据均拒绝或剥离。`x-opencode-session` 等经验证的协议头仅由对应来源适配路径传递。
3. 入口根据候选的连接状态、HTTP 状态和错误类型判断是否切换。流式连接须在收到可用的协议数据后才向客户端提交响应，之后发生错误按流中断处理。入口保留取消信号与背压。默认连接超时 5 秒、完整请求期限 120 秒，首版单候选不额外重试。客户端断连时取消上游并记录已知使用量。
4. 在普通响应与受支持的 SSE 事件中，将面向客户端的 `model` 字段统一为业务别名。保留供应商响应 ID 和其他兼容字段。实际来源和原模型 ID 通过调用详情及测试结果查看。入口透传允许的响应头和 `X-Request-Id`，返回符合 OpenAI SDK 的错误形状。

| 场景 | 执行方式 |
| --- | --- |
| 连接失败、可重试 `429`、上游临时 `5xx`、明确的模型不可用 | 回退到下一项，受总时间和候选数约束 |
| 通用 `400/422`、输入过长、策略拒绝、自定义工具不兼容 | 返回本次失败，保留明确错误信息 |
| 上游鉴权失败 | 记录来源凭证错误并触发预警。首版返回失败，管理员可在测试环境确认替代来源后发布 |
| 开始向客户端输出 SSE 后出现错误 | 结束流并记为 `interrupted`，保留已发送片段及可用 token |
| 使用上游会话状态或 `previous_response_id` | 仅在来源和模型亲和可经验证时接受。首版要求调用方提交完整上下文，拒绝依赖远程状态的请求 |
| 全部候选耗尽 | 返回映射后的上游错误，按请求 ID 查询各次尝试 |

后台可获取两层信号。实时回退对应单次调用，并在尝试日志中显示触发原因。目录确认下架后发布新的配置版本，后续请求可直接从下一可用候选开始。 [LiteLLM Responses API](https://docs.litellm.ai/docs/response_api)
