# 审计、用量与回放

## 采集与状态

推理入口在环境鉴权完成后创建逻辑调用，记录 `request_id`、环境、功能点、路由版本、端点、流式标识和调用类型。环境审计开关在请求开始时取快照。开启后保留入口改写之前的请求和客户端可见的最终响应。LiteLLM 回调写入每次实际尝试，至少提供关联 ID、来源模型、时间、失败类型和已报告的 usage。

入口在每次调用 LiteLLM 前分配尝试 ID，并用同值设置 `X-LiteLLM-Call-Id`。注册的回调使用 `litellm_call_id` 回填对应尝试，由 Minato 将多次尝试归到同一个业务请求。测试中 Proxy 原生回退的两次回调共享 `litellm_call_id`，各自的 `trace_id` 不同，业务自定义请求头在备用回调里也可能缺失。 [本地验证结果](../../tools/litellm-compat/README.md)

入口的采集写入和 LiteLLM 回调独立重试。采用有界队列和 Postgres 批量写入，按 `producer + eventId` 去重，以 `(request_id, attempt_id)` 合并尝试。`call.started`、`attempt.finished`、`call.finished`、`content.stored` 可以乱序抵达。先到的事件按 ID 暂存并对账，终态事件更新已有记录。进入队列但尚未持久化的事件可能在进程退出时丢失。需记录丢失计数，已创建的调用超过对账窗口后标记采集不完整。审计采集失败与推理成功或失败分别呈现。

| 维度 | 状态 |
| --- | --- |
| 调用 | `started`、`succeeded`、`failed`、`interrupted`、`cancelled`、`unknown` |
| 每份正文 | `disabled`、`pending`、`captured`、`partial`、`truncated`、`unavailable`、`expired` |
| 用量 | 模型报告值或 `null`，缺失情况按尝试统计 |

入口在转发 SSE 时按 Chat Completions 或 Responses 的事件结构重建正文，包括文本及工具调用参数。审计写入使用有界缓冲，超限后继续透传。调用提前中断时保留采集到的片段，已发送和上游已生成的范围可能不同。非 JSON 的错误响应在受限长度内按文本保存。认证失败只留安全事件所需元数据，未获得项目身份的请求不采集正文。

## 内容与导出

环境审计默认关闭。开启后默认留存 7 天，允许项目配置保留期和正文大小。请求、响应分别限制在 256 KiB 的默认采集预算内。元数据默认保留 90 天，两套保留期独立。配置更新作用于后续调用。管理员删除正文或后台清理到期正文后，关联用量与调用状态可继续查询。

正文进入持久化队列前先删除认证头、Cookie 和凭证字段，再套用环境脱敏规则。正文用独立服务密钥加密，仅向授权环境成员返回，读取和主动导出记操作日志。常规应用日志保存请求 ID、状态和计数。LiteLLM 的默认用量日志、回调和调试输出也需用测试样本验证，保证正文仅按 Minato 审计策略进入存储。

复制单条消息保留文本，复制完整 Prompt 用带角色的结构保留 system、developer、user、assistant 和 tool 消息顺序。复制请求 JSON 使用原客户端协议及可导出的参数。截断或脱敏内容在详情和导出预览标出，模型别名仍使用用户可调用的形式。

## Token 和成本口径

| 指标 | 计算方式 |
| --- | --- |
| 业务请求数 | 按 `calls.request_id`，正常业务、测试与回放可分别筛选 |
| 上游尝试数 | 按 `request_id + attempt_id` 去重。同一次回退可产生多笔尝试 |
| Token 汇总 | 使用上游报告的 input、output、cached、reasoning 及 total 字段。缓存和推理细项按供应商语义展示，避免加到 total 上二次计数 |
| 未知用量 | 同时返回缺少 usage 的尝试数及已知 token 合计。响应终态的 usage 只有确定属于某次尝试时才用于补齐该尝试 |
| 费用 | 上游报告或价格表估算分别标记，缺价格或用量时显示未知 |

CPA Usage Keeper 的账号侧统计用于核对和排障，Minato 的业务汇总使用自身调用记录。首版按受限日期范围直接聚合 Postgres，正式集成验收查询延迟后再决定是否增设每日汇总。

## 测试与回放流程

1. 新建测试或从记录载入。历史回放需要原记录内容权限。编辑器保留原端点、消息和参数，可修改 Prompt、温度或结构化输出参数。对已脱敏、截断、历史会话或失效附件标明缺失项，用户补成自包含且合法的文本请求后才能提交。
2. 提交 `featureId`、`endpoint`、`request`、`target`，可附 `replayOf`。`target.mode` 为 `active_route` 或 `specific_model`。前者在任务开始时绑定当前生效版本，后者要求 `sourceId + modelId` 属于当前环境允许范围并满足该请求能力。指定模型使用单候选测试路由，结果明确归属于该候选。
3. 服务端校验环境授权、可用模型和限额，接受 `Idempotency-Key`，先保存测试记录和新请求 ID，再由单任务执行。任务状态为 `queued → running → succeeded/failed/unknown`。执行后进程崩溃且无法确认上游是否已接收时进入 `unknown`，通过请求 ID 对账。用户可以显式发起新的测试。
4. 回放通过 Minato 推理入口执行，使用短期、限定测试环境和请求 ID 的内部凭证，实际使用量计入该环境。编辑器提交前显示具体请求、目标来源及模型。模型返回的工具调用在测试结果中展示，由人工查看。
5. 测试页并排展示原始和新结果，包含输出、实际模型、路由版本、耗时、token 和结构化校验状态。记录发起人、`replayOf`、输入变更摘要与结果。使用独立测试内容保留期限，默认 24 小时，普通业务正文审计仍按环境策略处理。

首版支持单次测试和单次回放。企业扩展沿用这些测试记录构建评测集，支持批量运行、限额控制和模型对比。 [产品需求](../requirements.md#调用审计与回放)
